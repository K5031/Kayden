# Agent Note: Duties

Status: proposed — a conversation can be given standing work, which it plans, paces and continues by itself until a person stops it

## Problem

[PHILOSOPHY.md](../../../PHILOSOPHY.md) makes Kayden the unit of a fleet (KFM) that works
without supervision: on a goal until it is reached, or on a duty ("be the marketing team")
indefinitely, creating its own tasks. Each unit, the top one especially, has to decide by
itself what to do next; the fleet manager only carries messages. Today a conversation
cannot do that:

- **It never starts work on its own.** It wakes only when the background work it started
  has all finished (SPEC 5.1, 5.2); after that it waits for a message.
- **It cannot react to the outside world.** A real team works from what comes in (email,
  a metric, a request) and from a plan. Kayden has neither: an idle agent waits for every
  outstanding operation, so a watcher that may wait for hours blocks every other wake-up,
  and nothing it decides persists except as text that compaction summarizes away.
- **Nobody can see where the work stands** without reading the transcript, which a
  supervisor, a person or the KFM, cannot do for a fleet.

A duty is also useful without a fleet: one window that keeps an inbox answered or a
project moving.

## Proposal

A duty is three things: a standing instruction, a plan the agent keeps, and the watchers
it runs. Only the plan is new; watchers are ordinary tools.

### Turning it on and off

- Only a person turns a duty on: a control on the conversation in the desktop app,
  `/duty <instruction>` in the TUI, or a launch option (`kd --duty "…"`) for a headless
  unit, which is how a spawner gives one. The model has no tool to start a duty; it may
  suggest one.
- A duty is one of two kinds. **Duty** runs until a person turns it off. **Goal** also
  ends when the agent declares it reached, with a short report.
- A duty needs a spending limit (`Budget.max_cost_usd`): turning one on without it is
  refused with a message saying so. The duration budget counts only active time, so it
  does not cap an agent that runs for days.
- Turning it on starts a cycle at once, as activation does.

### Pausing

- **Stop** pauses the duty: Stop already disables automatic wake-ups. Activating the
  conversation, or sending a message, resumes it.
- **An exhausted budget** pauses it with its reason (`Failure(BUDGET)`).
- **A restart or crash** leaves it paused until a person resumes it, as SPEC 11 requires
  for every conversation: a crash never silently re-runs a half-finished action. A
  launch with `--duty` is that person's action.

### The plan

- A list of items, each with text, a status (todo, doing, done, dropped), an optional
  note and an optional due time. It belongs to the conversation and is shown in full in
  every request, after the duty's instruction, so compaction never loses it.
- The agent changes it with a runtime built-in tool (`update_plan`), like `op_status`:
  the plan is orchestration state, not memory. Built-ins are never gated and do not count
  as tool calls.
- The user sees it and edits it in the app; a `PlanChanged` event tells frontends.
- The plan is the report: a supervisor reads it to know where the work stands. A goal's
  final report goes with it.
- Memory stores the duty and its plan as conversation metadata (`ConversationInfo.duty`,
  set through `update_conversation`), like the work folder. Memory persists it and knows
  nothing of its meaning; the runtime reads it to schedule.

### Waking up

A duty conversation wakes on whichever comes first:

- **A watcher finishing.** A watcher is any tool that runs in the background and finishes
  when something happens: new email from an MCP server, a webhook, a file change through
  a shell command. In a duty conversation the agent wakes when any outstanding operation
  terminates, not when all have. A watcher that times out wakes it too, and the agent
  starts another.
- **A message** from the user (or later the KFM), as today.
- **The schedule:** the earliest due time among open plan items, held between a minimum
  and a maximum interval after the cycle ends. With nothing due it wakes at the maximum,
  so a duty never stalls silently. Both intervals are set with the duty; their defaults
  are recorded in `.agents/decisions.md` when built.

Each wake is logged in the event log with its cause.

### Spec changes

- SPEC 5.1 "The runtime never re-prompts on its own": except on a duty's schedule.
- SPEC 5.2 batch wake-up: holds outside duties; a duty conversation wakes on the first
  terminated operation.
- SPEC 13: "Scheduled wake-ups" leaves the out-of-scope list; duties are added to the
  product vision (section 1) and get a section of their own.
- SPEC 11 (a restart starts nothing) is kept.
- api.py: `Duty` and plan types, `ConversationInfo.duty`, `update_conversation(duty=…)`,
  `RuntimeAPI` calls to set, clear and edit a duty, the `update_plan` built-in and a
  goal's finish tool, `PlanChanged`, `--duty` on the launchers.

The scope question PHILOSOPHY.md raises against SPEC 10.2 and 13 is in
`.agents/contract-issues.md` (section 14).

## Alternatives considered

- **The KFM drives it,** sending "continue" or the next task. Kayden would stay as it is,
  but the judgment of what to do next would move into the fleet manager, which is meant
  only to carry messages, and a single Kayden could not hold a duty at all.
- **A fixed heartbeat** ("every 30 minutes"). Predictable, but it wakes when nothing
  happened and is late when something did; the maximum interval keeps its one advantage,
  that the agent can never stall.
- **A "wake me in…" tool without a plan.** Simpler, but what the agent decided would
  still live only in the transcript, nobody could see where the work stands, and the
  agent forgets to call it.
- **The plan as a memory note.** Notes are long-term memory shared by every conversation,
  and the runtime could not read due times from them without knowing how a Memory module
  stores notes.
- **A watcher flag on `ToolSpec`,** so only watchers wake early and other background work
  keeps the batch rule. Fewer wake-ups when a duty runs parallel jobs, but MCP servers
  cannot set the flag, and waking early only costs a turn that ends at once.
- **The model may turn a duty on.** Convenient ("keep doing this"), but a vague message
  could start something that spends money indefinitely.
- **A separate mode,** as Continuous Mode was. Retired for good reasons
  ([autonomy into sessions](../implemented/2026-11-07-autonomy-into-sessions.md)): a duty
  is an ordinary conversation the user still curates, archives or deletes.

## Acceptance criteria

- A person turns a duty on; the model cannot. Without a spending limit it is refused.
- A duty conversation with a running watcher and a due plan item wakes on whichever
  comes first, and logs the cause.
- With nothing due and nothing running, it wakes at the maximum interval.
- Stop, an exhausted budget and a restart each leave it paused until a person resumes it.
- The plan survives compaction and restarts, is shown in every request, and the user can
  edit it.
- A goal ends when the agent declares it reached; a duty does not.
- Conversations without a duty behave exactly as today (Scenario E still holds).

## Risks

- **Cost.** An agent that never stops spends money as long as it runs; the spending
  limit is the guard, and a duty cannot start without one.
- **Drift.** Over days the plan and summary can wander from the instruction. The
  instruction is shown in full every request, and the plan is visible, but nothing
  detects drift yet.
- **Wake-ups with nothing to do** still cost a request each, mostly the context. The
  minimum interval and a sensible maximum keep that bounded.
- **Watchers that finish too often** (a busy inbox) wake the agent on every change; the
  minimum interval does not hold them back.
