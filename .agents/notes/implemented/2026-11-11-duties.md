# Agent Note: Duties

Status: implemented — a person gives any conversation standing work, which the agent plans, paces and carries on by itself until it is paused or ended

## Problem

[PHILOSOPHY.md](../../../PHILOSOPHY.md) makes Kadence the unit of a fleet (KFM) that works
without supervision: on a goal until it is reached, or on a duty ("be the marketing team")
indefinitely, creating its own tasks. Each unit, the top one especially, has to decide by
itself what to do next; the fleet manager only carries messages. A conversation could not
do that:

- **It never started work on its own.** It woke only when all the background work it
  started had finished; after that it waited for a message.
- **It could not react to the outside world.** A real team works from what comes in
  (email, a metric, a request) and from a plan. An idle agent waited for every outstanding
  operation, so a watcher that may wait for hours blocked every other wake-up, and nothing
  it decided persisted except as text that compaction summarizes away.
- **Nobody could see where the work stood** without reading the transcript, which a
  supervisor, a person or the KFM, cannot do for a fleet.

A duty is also useful without a fleet: one window that keeps an inbox answered or a
project moving.

## Decision

A duty is a standing instruction, a plan the agent keeps, and the watchers it runs. Only
the plan is new; watchers are ordinary tools.

### Turning it on and off

- Only a person sets a duty: `RuntimeAPI.set_duty`, from **Kadence → Duty…** in the
  desktop app or `/duty`, `/goal` and F5 in the TUI. The model has no tool to start one.
  What the model can do in any conversation is give a step of its plan a due time
  (see Reminders).
- `api.Duty` has an instruction, a kind and two intervals. **Duty** runs until a person
  ends it; **goal** also ends when the agent calls `finish_goal` with a short report.
- A spending limit (`Budget.max_cost_usd`) is the user's choice: a duty runs without one,
  as nothing in Claude's apps requires a limit to work unattended (the user, 2026-11-12:
  the requirement was annoying). With one set, reaching it stops the duty like any work.
  The duration budget counts only active time, so it does not cap an agent that runs for
  days.
- Any conversation can take on a duty at any time, keeping everything said so far, and
  drop it again. Turning one on while idle, stopped or failed (not by budget) starts a
  cycle at once; a change during a cycle applies when it ends.
- Ending a duty keeps the plan, shown and editable. "Continue from" copies neither.

### Pausing

- **Stop** pauses the duty: it ends the schedule, even with nothing running. A message or
  activation resumes it.
- **A failure or an exhausted budget** pauses it with the failure's reason.
- **A restart or crash** leaves it paused until a person resumes it, as for every
  conversation (SPEC 11): a crash never silently re-runs a half-finished action.

### The plan

- `api.PlanItem`: text, status (todo, doing, done, dropped), optional due time and note.
  The agent replaces the whole list with the runtime built-in `update_plan`, offered while
  the conversation has a duty or a plan; the user edits it with `RuntimeAPI.set_plan`.
- Every request shows the duty's instruction after Memory's addendum. The plan is in view
  through the agent's own `update_plan` call while that call is among the request's
  messages; otherwise (the user edited it, the conversation was opened again, the call was
  summarized away) it follows the duty in the system prompt. Compaction never loses it,
  and an update does not change the prompt, which keeps the provider's cache valid.
- The duty and plan are conversation metadata (`ConversationInfo.duty`, `plan`), stored
  by the optional `Memory.save_duty`. Memory knows nothing of their meaning; the runtime
  reads them to schedule. Changes emit `ConversationUpdated`.
- The plan is the report: a supervisor reads it to know where the work stands.

### Waking up

A conversation with a duty wakes on whichever comes first:

- **An operation finishing.** In a duty conversation the agent wakes when the first
  outstanding operation terminates, not the whole batch. A watcher is any tool that waits
  in the background and finishes when something happens: new mail from an MCP server, a
  webhook, a file change through a shell command. One that times out wakes it too.
- **A message**, as always.
- **The schedule:** the earliest due open plan item, held between the minimum and maximum
  interval after the cycle ends; with nothing due, the maximum. A duty never stalls
  silently. `DutyScheduled` and `RuntimeSnapshot.duty_wake_at` say when it wakes next.

### Asking for help

When it is blocked and only its supervisor can unblock it (a decision, an approval,
access it lacks), the agent calls the built-in `ask_for_help` with one question. The
schedule then pauses, so a stuck agent does not wake every interval to find itself still
stuck; finished operations still wake it. `HelpNeeded` and
`RuntimeSnapshot.help_needed` carry the question, and frontends show it. A message, an
activation or a change of duty answers it and the schedule resumes.

Whoever drives the instance is its supervisor. Today that is the user. In a fleet the KFM
routes the question to the unit's supervisor, which resolves it or asks its own, up to a
human only when no unit can resolve it ([PHILOSOPHY.md](../../../PHILOSOPHY.md)). Kadence
stays the same: it asks and waits for a message.

### Notices

A cycle the runtime starts for a duty begins with a notice that gives the cause, and the
event log records each cause. The agent knows the time because every user message, notices
included, reaches the model with the time it was sent; the current time is not in the
system prompt, where it would change every request and void the provider's prompt cache.

A launch option that starts a headless unit on its duty belongs to the headless frontend,
the next step toward the KFM.

### Reminders

Without a duty, an open step that falls due still wakes the agent, once
(`duties.next_reminder`, `duties.reminder`): the user asked for "remind me at 9" to work
in an ordinary chat (2026-11-12). The same timer as a duty's is used
(`Runtime._schedule_duty`), with no check-ins:

- A step reminds once: steps due up to the last reminder (`Runtime._reminded`) do not wake
  again, so one left open does not loop.
- Not sooner than `RuntimeConfig.reminder_min_s` (a minute) after a turn ends.
- `update_plan`'s answer says that a due step will wake the agent (`duties.WAKES`). An
  agent that gives itself a new due step at every wake-up is a duty in all but name; a
  spending limit, when the user sets one, bounds it.
- Opening a conversation counts every step already due as reminded: it waits for the
  user, as a duty does after a restart, so a crash never repeats an action. Steps still
  ahead are scheduled.
- Stop and a failure put reminders off until the next cycle ends.
- Frontends show the next one from `DutyScheduled` and `duty_status` ("Reminder at …").

## Alternatives considered

- **The KFM drives it,** sending "continue" or the next task. Kadence would stay as it was,
  but the judgment of what to do next would move into the fleet manager, which is meant
  only to carry messages, and a single Kadence could not hold a duty at all.
- **A fixed heartbeat** ("every 30 minutes"). Predictable, but it wakes when nothing
  happened and is late when something did; the maximum interval keeps its one advantage,
  that the agent can never stall.
- **Requiring a spending limit for a duty and for reminders.** Built first: `set_duty`
  refused without one. It guards against a looping agent, but it made the limit a chore
  for everything unattended, and the limit is a lifetime total that then blocks ordinary
  chats too. The user chose Claude's way: optional, with the account's limit as backstop.
- **Due steps that wake only with a duty.** The first design: nothing made the agent act
  unless a person had turned a duty on. But the agent set due times anyway and waited for
  a wake-up that never came, and "remind me" is a natural thing to ask in any chat.
- **A "wake me in…" tool without a plan.** Simpler, but what the agent decided would live
  only in the transcript, nobody could see where the work stands, and the agent forgets to
  call it.
- **The plan as a memory note.** Notes are long-term memory shared by every conversation,
  and the runtime could not read due times from them without knowing how a Memory module
  stores notes.
- **A watcher flag on `ToolSpec`,** so only watchers wake early and other background work
  keeps the batch rule. Fewer wake-ups when a duty runs parallel jobs, but MCP servers
  cannot set the flag, and waking early only costs a turn that ends at once.
- **No way for the agent to pause.** Simpler, and the agent could never give up on
  standing work, but a blocked agent would wake every interval, find itself still
  blocked and spend a request each time.
- **The model may turn a duty on.** Convenient ("keep doing this"), but a vague message
  could start something that spends money indefinitely.
- **A duty fixed when the conversation is created.** Clearer for a spawned unit, but a
  conversation that grew into standing work would have to start over without its context,
  and a spawned unit is only the case of turning it on with the first message.
- **A separate mode,** as Continuous Mode was. Retired for good reasons
  ([autonomy into sessions](2026-11-07-autonomy-into-sessions.md)): a duty is an ordinary
  conversation the user still curates, archives or deletes.

## Consequences

- One conversation can work for days without a person, and a person can see its plan and
  its next check-in at any time.
- **Cost.** An agent that never stops spends money as long as it runs. The guards are a
  spending limit, if the user sets one, and the provider's own spend limit; without
  either, nothing stops a duty that loops. Each wake with nothing to do still costs a request, mostly the context.
- **Unattended means permissions that cover the work.** A call that would prompt waits
  for the user; sending prompts to a supervisor is part of the headless frontend.
- **Drift.** Over days the plan and summary can wander from the instruction. The
  instruction is shown in full every request and the plan is visible, but nothing detects
  drift.
- **The agent may ask too readily.** A question pauses the schedule until someone answers;
  answering is one message, and the prompt tells it to solve what it can first.
- **Busy watchers** (a busy inbox) wake the agent on every change; the minimum interval
  holds back only the schedule.
- A plan change voids the provider's prompt cache for the messages after the system
  prompt, once per change.
- Memory has one more optional method and the SQLite store one more schema (8).
